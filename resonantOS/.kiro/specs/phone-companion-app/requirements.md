# Requirements Document

## Introduction

The Phone Companion App turns iOS and Android phones into active compute nodes within the ResonantOS mesh network. Phones contribute their ARM CPUs, NPUs (Apple Neural Engine, Qualcomm Hexagon), and RAM to the distributed inference cluster. The app is built with Tauri Mobile v2, reusing the existing React frontend and Rust backend. The critical capability is splitting a single model across multiple phones using the existing Split Inference Protocol (Phase 11), enabling phones with a 3GB model size restriction to collectively run larger models (e.g., a 7B model split across 2-3 phones).

## Glossary

- **Companion_App**: The Tauri Mobile v2 application running on iOS/Android that participates as a compute node in the ResonantOS mesh network.
- **Phone_Node**: A phone device registered in the mesh network registry as a compute participant.
- **Coordinator**: The desktop node that manages model placement, session orchestration, and health monitoring for the mesh.
- **Split_Inference_Engine**: The subsystem that divides a model's layers across multiple nodes and coordinates activation forwarding between them.
- **Layer_Worker**: The component on a Phone_Node responsible for executing its assigned subset of model layers during split inference.
- **Inference_Runtime**: The lightweight inference engine (llama.cpp compiled for ARM/NPU) running on the phone.
- **Pairing_Flow**: The QR code-based onboarding process (Phase 9C) that registers a phone with the mesh using a 5-minute single-use token and subnet verification.
- **Transport_Adapter**: A communication channel (LAN, WireGuard, or Reticulum) used to exchange data between mesh nodes.
- **Health_Reporter**: The component that periodically sends battery level, thermal state, connectivity, and resource utilization to the Coordinator.
- **NPU**: Neural Processing Unit — dedicated hardware accelerator for inference (Apple Neural Engine on iOS, Qualcomm Hexagon/Mali GPU on Android).
- **Model_Assignment**: A placement decision from the optimizer specifying which model (or model layers) a Phone_Node should load and execute.

## Requirements

### Requirement 1: Store-Independent Distribution

**User Story:** As a user, I want to install the companion app without depending on the Apple App Store or Google Play Store, so that I can freely participate in the mesh network without store approval constraints.

#### Acceptance Criteria

1. THE Companion_App SHALL be packaged as a Tauri Mobile v2 application targeting both iOS and Android platforms.
2. THE Companion_App SHALL produce a sideloadable APK artifact for Android distribution.
3. THE Companion_App SHALL produce an IPA artifact compatible with TestFlight and enterprise certificate distribution for iOS.
4. THE Companion_App SHALL reuse the existing React frontend components and Rust backend modules from the desktop application.
5. THE Companion_App SHALL compile the Rust backend for ARM64 (aarch64) architecture on both platforms.

### Requirement 2: Mesh Network Connection

**User Story:** As a user, I want my phone to connect to the mesh network using the existing QR code pairing flow, so that joining is quick and secure.

#### Acceptance Criteria

1. WHEN the user scans a QR code generated by the desktop Coordinator, THE Companion_App SHALL initiate the Pairing_Flow by sending a handshake containing the pairing token, phone node ID, and phone capabilities.
2. WHEN the Pairing_Flow completes successfully, THE Companion_App SHALL register as a Phone_Node in the mesh network registry with device type, NPU capabilities, RAM, battery level, and connection type.
3. WHILE connected to the mesh, THE Companion_App SHALL maintain a persistent connection to the Coordinator via the Transport_Adapter (LAN, WireGuard, or Reticulum).
4. IF the pairing token has expired (older than 5 minutes), THEN THE Companion_App SHALL display an error message and prompt the user to request a new QR code.
5. IF the phone is not on the same subnet as the desktop during LAN pairing, THEN THE Companion_App SHALL reject the pairing attempt and display the subnet mismatch to the user.
6. WHEN the Companion_App reconnects after a network interruption, THE Companion_App SHALL re-authenticate with the Coordinator using the stored mesh identity without requiring a new QR code scan.

### Requirement 3: On-Device Inference Execution

**User Story:** As a user, I want my phone to run AI inference locally using its NPU or CPU, so that it contributes real compute power to the mesh.

#### Acceptance Criteria

1. THE Inference_Runtime SHALL embed llama.cpp compiled for ARM64 with platform-specific NPU acceleration (Core ML on iOS, NNAPI/Qualcomm QNN on Android).
2. WHEN the Coordinator sends a Model_Assignment for a full model (≤3B parameters), THE Inference_Runtime SHALL download the model weights and load them into memory.
3. WHEN an inference request arrives for a locally-loaded model, THE Inference_Runtime SHALL execute the full forward pass and return the result to the requesting node via the Transport_Adapter.
4. THE Inference_Runtime SHALL enforce a maximum model size of 3GB in memory to prevent out-of-memory termination by the mobile OS.
5. IF the Inference_Runtime detects an out-of-memory condition during model loading, THEN THE Inference_Runtime SHALL abort the load, release allocated memory, and report the failure to the Coordinator.

### Requirement 4: Split Inference Participation

**User Story:** As a user, I want multiple phones to collaboratively run a single large model by splitting it across them, so that I can run 7B+ models that no single phone could handle alone.

#### Acceptance Criteria

1. WHEN the Coordinator assigns a layer range to the Phone_Node via the Split Inference Protocol, THE Layer_Worker SHALL load only the assigned layer weights into memory.
2. WHEN the Layer_Worker receives an activation tensor from the preceding node in the pipeline, THE Layer_Worker SHALL execute its assigned layers and forward the output activation to the next node.
3. THE Layer_Worker SHALL support both tensor parallel mode (for inter-phone latency <5ms) and pipeline parallel mode (for inter-phone latency 5-50ms) as determined by the Coordinator.
4. WHILE participating in a split inference session, THE Layer_Worker SHALL respond to activation forwarding requests within the session's timing budget (calibrated during the 5-token warmup phase).
5. IF the Layer_Worker fails to process an activation within the timeout, THEN THE Layer_Worker SHALL report the timeout to the session Coordinator and release the session resources.
6. THE Split_Inference_Engine SHALL support splitting a 7B parameter model (~5GB) across 2-3 Phone_Nodes, with each node holding at most 3GB of layer weights.
7. WHEN a split inference session is initiated, THE Layer_Worker SHALL participate in the 5-token calibration warmup to measure actual inter-node latency and compute timing.

### Requirement 5: Model Assignment Acceptance

**User Story:** As a user, I want my phone to automatically accept and execute model assignments from the optimizer, so that the mesh can efficiently utilize my phone's resources without manual intervention.

#### Acceptance Criteria

1. WHEN the Coordinator sends a Model_Assignment, THE Companion_App SHALL validate that the assignment is compatible with the phone's current constraints (available memory, battery level, connection type).
2. IF the Model_Assignment exceeds the phone's available memory, THEN THE Companion_App SHALL reject the assignment and report the constraint violation to the Coordinator.
3. IF the phone's battery is below the configured threshold (default 20%) and the phone is not charging, THEN THE Companion_App SHALL reject new Model_Assignments and notify the Coordinator of the battery constraint.
4. WHEN a Model_Assignment is accepted, THE Companion_App SHALL download the required model weights (or layer weights for split inference) and report readiness to the Coordinator.
5. WHEN the Coordinator sends an unload command, THE Companion_App SHALL release the model weights from memory and confirm the unload to the Coordinator.

### Requirement 6: Health and Battery Reporting

**User Story:** As a user, I want my phone to report its health status to the mesh coordinator, so that the optimizer can make informed placement decisions and avoid draining my battery.

#### Acceptance Criteria

1. WHILE connected to the mesh, THE Health_Reporter SHALL send a health heartbeat to the Coordinator every 30 seconds containing battery percentage, charging state, thermal state, connection type, available memory, and current CPU/NPU utilization.
2. WHEN the battery level drops below the configured threshold (default 20%) and the phone is not charging, THE Health_Reporter SHALL send an immediate low-battery alert to the Coordinator.
3. WHEN the phone transitions between WiFi and cellular connectivity, THE Health_Reporter SHALL send an immediate connectivity-change notification to the Coordinator.
4. IF the phone enters a thermal throttling state, THEN THE Health_Reporter SHALL report the thermal condition and reduced compute capacity to the Coordinator.
5. WHEN the Coordinator does not receive a heartbeat from the Phone_Node for 90 seconds, THE Coordinator SHALL mark the Phone_Node as offline and reassign its workload.
6. THE Health_Reporter SHALL include the phone's current inference load (active sessions, tokens per second) in each heartbeat.

### Requirement 7: Background Execution and Lifecycle

**User Story:** As a user, I want the companion app to continue contributing compute even when in the background, so that the mesh remains stable without requiring me to keep the app in the foreground.

#### Acceptance Criteria

1. WHILE the Companion_App is in the background on iOS, THE Companion_App SHALL use Background Processing tasks to maintain mesh connectivity and complete in-progress inference requests.
2. WHILE the Companion_App is in the background on Android, THE Companion_App SHALL use a foreground service with a persistent notification to maintain mesh connectivity and inference execution.
3. WHEN the mobile OS terminates the Companion_App due to resource pressure, THE Companion_App SHALL persist its mesh identity and pairing state so that it can rejoin without re-pairing on next launch.
4. WHEN the user explicitly stops the Companion_App, THE Companion_App SHALL send a graceful leave notification to the Coordinator before shutting down.
5. IF the Companion_App is suspended by the OS during an active split inference session, THEN THE Companion_App SHALL notify the session Coordinator within 5 seconds so the session can failover.

### Requirement 8: Transport Layer Integration

**User Story:** As a user, I want my phone to communicate with other mesh nodes using the best available transport, so that inference data flows efficiently regardless of network topology.

#### Acceptance Criteria

1. THE Companion_App SHALL implement the Transport_Adapter trait to support LAN (mDNS/TCP), WireGuard, and Reticulum transport channels.
2. WHEN multiple transport paths are available, THE Companion_App SHALL use the path selector to choose the lowest-latency path for inference activation forwarding.
3. IF the active transport path fails, THEN THE Companion_App SHALL failover to the next available transport within 100ms.
4. THE Companion_App SHALL report per-path latency and bandwidth metrics to the transport registry for path selection optimization.
5. WHEN forwarding split inference activations, THE Companion_App SHALL use the Critical message priority to ensure lowest-latency routing.

### Requirement 9: Security and Identity

**User Story:** As a user, I want my phone's communication with the mesh to be encrypted and authenticated, so that my inference data remains private.

#### Acceptance Criteria

1. THE Companion_App SHALL generate and store an Ed25519 keypair as its persistent mesh identity upon first pairing.
2. THE Companion_App SHALL encrypt all transport-layer communication using end-to-end encryption with forward secrecy.
3. THE Companion_App SHALL store the mesh identity keypair in the platform's secure enclave (iOS Keychain / Android Keystore).
4. WHEN the Companion_App connects to a mesh node, THE Companion_App SHALL authenticate using mutual TLS or the mesh identity signature.
5. THE Companion_App SHALL join the mesh as a Tier 1 (LocalOwned) trust level node after pairing with the owner's desktop.

### Requirement 10: NPU Detection and Acceleration

**User Story:** As a user, I want the app to automatically detect and use my phone's NPU for inference, so that I get the best possible performance from my hardware.

#### Acceptance Criteria

1. WHEN the Companion_App starts, THE Companion_App SHALL detect available hardware accelerators: Apple Neural Engine (iOS), Qualcomm Hexagon DSP, Qualcomm QNN, or Mali GPU (Android).
2. THE Companion_App SHALL report detected NPU type and generation to the Coordinator as part of the phone capabilities during pairing and in health heartbeats.
3. WHEN loading a model for inference, THE Inference_Runtime SHALL prefer NPU execution over CPU when the model format supports it and the NPU is available.
4. IF NPU execution fails or is unavailable, THEN THE Inference_Runtime SHALL fall back to CPU-based inference and report the degraded compute capacity to the Coordinator.
5. THE Companion_App SHALL report a compute speed benchmark (tokens per second for a reference model) during initial pairing so the optimizer can accurately assign layer counts.
